## 2. Призначення програми

Програма допомагає родині вести спільний бюджет. Власник бюджету (наприклад, один із батьків) бачить баланс кожного рахунку, записує доходи й витрати за категоріями та розглядає заявки інших членів родини на витрати. Член родини (наприклад, дитина-студент) бачить, скільки грошей є на рахунках, відкритих для заявок, подає заявку на витрату й стежить за рішенням.

Баланс рахунку змінюється автоматично під час проведення операції та схвалення заявки, тому вручну його перераховувати не потрібно.

Усі суми, рахунки, імена й операції — вигадані навчальні дані. Реальні банківські дані, номери карток і платежі в програмі не використовуються, оплату лише моделюють.

## 3. Користувачі та сторінки

| Користувач | Сторінка | Що робить |
| --- | --- | --- |
| Член родини | `client.html` | Переглядає рахунки, відкриті для заявок; подає заявку на витрату; перевіряє статус своїх заявок; скасовує власну нову заявку |
| Власник бюджету | `admin.html` | Схвалює або відхиляє заявки; керує рахунками й категоріями; веде журнал доходів і витрат із пошуком, фільтрами та сортуванням |

Реєстрація, вхід і ролі не передбачені. Дві сторінки — це дві частини інтерфейсу, а не захист доступу: сервер не перевіряє, хто надсилає запит.

## 4. Задача, яку розв'язує програма

Без програми рішення про витрати приймають усно, а облік ведуть у зошиті. Важко зрозуміти, скільки грошей залишилося на кожному рахунку, хто і на що просив гроші, і легко погодити витрату, на яку грошей уже немає. Програма:

- зберігає рахунки, категорії, операції та заявки в одному місці (`db.json`);
- приймає заявки на витрату й показує їхній статус обом сторонам;
- **не дозволяє подати чи схвалити заявку і не проводить витрату, якщо на рахунку недостатньо коштів**;
- під час схвалення заявки сама списує гроші й записує операцію-витрату;
- дає змогу знайти, відфільтрувати й відсортувати операції.

**Основна операція предметної області — схвалення заявки на витрату** з перевіркою достатності коштів. Програма перевіряє `сума ≤ баланс рахунку`, списує суму, створює операцію-витрату й змінює статус заявки на «Схвалена». Повторна спроба схвалити ту саму заявку завершується повідомленням без зміни даних. Це аналог видачі книги в бібліотеці: там перевіряють наявність примірника, тут — наявність грошей.

## 5. Дані

Дані зберігаються у файлі `db.json`, який обслуговує JSON Server. Ідентифікатори — рядки (`"1"`, `"2"` …). Для нових записів id створює JSON Server: рядок із 7 випадкових символів, наприклад `"fTN1ZeS"`. Грошові суми — числа з не більше ніж двома знаками після коми, валюта одна — гривня (₴).

### 5.1 Колекція `accounts` — рахунки («пропозиції» для члена родини)

| Поле | Тип | Обмеження |
| --- | --- | --- |
| id | string | Унікальний, створює JSON Server |
| name | string | Обов'язкове, 2–40 символів після обрізання пробілів; унікальне без урахування регістру |
| type | string | `cash` (готівка), `card` (картка), `savings` (заощадження) |
| balance | number | ≥ 0 і ≤ 10 000 000. Під час створення — початковий залишок; далі змінюється лише через операції та схвалені заявки |
| openForRequests | boolean | `true` — рахунок видно члену родини, з нього можна просити витрату |

### 5.2 Колекція `categories` — категорії

| Поле | Тип | Обмеження |
| --- | --- | --- |
| id | string | Унікальний, створює JSON Server |
| name | string | Обов'язкове, 2–30 символів; унікальне в межах свого типу без урахування регістру |
| type | string | `income` (дохід) або `expense` (витрата); не змінюється, якщо категорію вже використано |

### 5.3 Колекція `transactions` — операції

| Поле | Тип | Обмеження |
| --- | --- | --- |
| id | string | Унікальний, створює JSON Server |
| type | string | `income` або `expense` |
| amount | number | > 0 і ≤ 1 000 000; не більше 2 знаків після коми |
| date | string | `РРРР-ММ-ДД`; реальна дата з 2000-01-01 до сьогодні |
| accountId | string | id наявного рахунку |
| categoryId | string | id наявної категорії; тип категорії збігається з типом операції |
| comment | string | Необов'язковий, до 100 символів |
| requestId | string | Є лише в операції, створеній під час схвалення заявки; таку операцію не можна змінити чи видалити |

### 5.4 Колекція `requests` — заявки на витрату

| Поле | Тип | Обмеження |
| --- | --- | --- |
| id | string | Унікальний, створює JSON Server |
| requesterName | string | Ім'я члена родини: 2–40 символів, лише літери, пробіл, апостроф, дефіс |
| accountId | string | id рахунку, відкритого для заявок |
| categoryId | string | id категорії витрат |
| amount | number | > 0 і ≤ 1 000 000; під час подання — не більше поточного балансу рахунку |
| purpose | string | Призначення витрати, 3–100 символів |
| status | string | `new`, `approved`, `rejected`, `cancelled` (див. розділ 7) |
| createdAt, updatedAt | string | Дата й час у форматі ISO 8601 |
| adminComment | string | Причина відхилення (3–100 символів) або порожній рядок |
| transactionId | string | Є лише у схваленій заявці — id створеної операції |

### 5.5 Зв'язки та правило роботи з пов'язаними записами

- Рахунок 1 — N операцій і 1 — N заявок (`accountId`).
- Категорія 1 — N операцій і 1 — N заявок (`categoryId`).
- Схвалена заявка 1 — 1 операція-витрата (`transactionId` ↔ `requestId`).

**Особливість JSON Server 0.17.4, перевірена в його коді.** Під час будь-якого `DELETE` сервер видаляє всі записи, у яких поле з закінченням `Id` посилається на неіснуючий запис або дорівнює `null`. Тому діють такі правила:

1. Рахунок або категорію, з якими пов'язані операції чи заявки, видалити не можна — програма показує, скільки записів пов'язано. Так історія фінансів не зникає разом із рахунком. Щоб рахунок не з'являвся у члена родини, його закривають для заявок.
2. Поля `…Id` ніколи не зберігаються з порожнім значенням: якщо зв'язку немає, поля немає взагалі.
3. Операцію, створену за заявкою, не можна змінити чи видалити — інакше заявка й баланс розійдуться.

## 7. Статуси заявки та допустимі переходи

| Поточний статус | Дія | Хто | Новий статус | Умова |
| --- | --- | --- | --- | --- |
| `new` (Нова) | Схвалити | Власник бюджету | `approved` (Схвалена) | `amount ≤ balance` рахунку на момент схвалення |
| `new` | Відхилити | Власник бюджету | `rejected` (Відхилена) | Причина 3–100 символів |
| `new` | Скасувати | Член родини | `cancelled` (Скасована) | — |
| `approved`, `rejected`, `cancelled` | будь-яка | — | — | Заборонено: кінцевий стан |

Переходи реалізовано патерном State (`js/request-states.js`). Детальніше — у `docs/design.md`.

## 8. Головне правило перевірки даних

> **Витрату можна провести лише тоді, коли її сума не перевищує поточний баланс рахунку: `amount ≤ account.balance`.**

Правило перевіряється тричі, щоразу на свіжих даних із сервера:

1. під час подання заявки (`createRequest`);
2. під час схвалення заявки (`approveRequest`) — баланс міг змінитися після подання;
3. під час проведення витрати власником (`conductTransaction`).

Якщо умова не виконується, нічого не зберігається, а користувач бачить, наприклад: «Недостатньо коштів на рахунку «Готівка»: доступно 1 016,60 ₴, потрібно 1 017,60 ₴. Заявку не схвалено — вона лишається новою».

Наслідок правила: **баланс рахунку ніколи не стає від'ємним**, у тому числі після редагування чи видалення операції.

## 10. Межі проєкту

**Входить:**

- дві сторінки (`client.html`, `admin.html`) зі спільними даними через JSON Server;
- заявки на витрату зі статусами та перевіркою допустимих переходів;
- облік рахунків, категорій і операцій з автоматичною зміною балансу;
- пошук, фільтрування й сортування операцій;
- перевірка введення та оброблення помилок сервера.

**Не входить:**

- реєстрація, вхід, ролі та серверний захист доступу;
- реальні банківські рахунки, платежі, імпорт виписок;
- кілька валют, переказ між рахунками;
- місячні бюджети категорій, звіт за період, експорт, історія змін — це можливості рівня IV;
- автоматичне оновлення сторінок і публікація в інтернеті: демонстраційна версія локальна, бо API на `localhost` доступне лише на комп'ютері, де запущено JSON Server.

## 11. Для чого потрібні Live Server і JSON Server

- **JSON Server 0.17.4** — навчальний REST-сервер. Він перетворює `db.json` на HTTP API за адресою `http://localhost:5000`: `GET /requests`, `GET /requests/1`, `POST`, `PATCH`, `DELETE`. Зміни записуються в `db.json`. Запуск: `npm run server` (те саме, що `npx json-server --watch db.json --port 5000`).
- **Live Server** (розширення VS Code) — локальний вебсервер для HTML, CSS і JavaScript (`http://127.0.0.1:5500`). Сторінки потрібно відкривати саме через нього: ES-модулі й запити `fetch` не працюють зі сторінки, відкритої подвійним кліком по файлу.

Це два незалежні сервери: JSON Server надає дані, Live Server — сторінки, а модулі з папки `js/` пов'язують їх HTTP-запитами.
