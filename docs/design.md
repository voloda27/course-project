# Проєктні рішення

Документ описує структуру програми «Сімейний бюджет», макети сторінок і два застосовані патерни: Repository та State (GoF). Вимоги — у [task.md](task.md).

**Стан реалізації (етап 3).** Сторінки зверстано, обидві читають дані з JSON Server через `FinanceRepository` (GET). Операції зміни в Repository і патерн State спроєктовано в цьому документі; їх буде реалізовано на етапі 4.

## 1. Архітектура

```
 client.html ─┐                     ┌─ HttpClient (js/api.js) ── fetch ──► JSON Server :5000 ──► db.json
              ├─ js/client.js ─┐    │
              │                ├──► FinanceRepository (js/repository.js)
 admin.html  ─┴─ js/admin.js ──┘    │
                                    ├─ ExpenseRequest + стани (js/request-states.js)   ← патерн State
                                    └─ checkFunds, validate… (js/validation.js)
```

Шари мають такі обов'язки:

- **Інтерфейс** (`client.js`, `admin.js`) читає форми, викликає перевірку введення, звертається до репозиторію й малює HTML. Адрес API і `fetch` тут немає.
- **Repository** (`repository.js`) виконує предметні операції. Він формує HTTP-запити, перевіряє правила на свіжих даних і відкочує зміни, якщо запит не вдався.
- **HttpClient** (`api.js`) — єдине місце, де викликається `fetch`. Він перевіряє `response.ok` і перетворює збої на помилки `ConnectionError`, `NotFoundError` та `HttpError`.
- **Дані** — `db.json`, який обслуговує JSON Server 0.17.4.

| Файл | Призначення |

## 2. Макети сторінок

### 2.1 `client.html` — член родини

1. **Рахунки родини.** Картки рахунків, відкритих для заявок, з балансом і кнопкою «Обрати для заявки». Є кнопка «Оновити рахунки».
2. **Нова заявка на витрату.** Поля: ім'я, рахунок, категорія витрати, сума, призначення. Кнопка «Надіслати заявку», під формою — місце для повідомлень.
3. **Мої заявки.** Поле імені й кнопка «Оновити», таблиця заявок зі статусом і коментарем власника. У нової заявки є кнопка «Скасувати».

### 2.2 `admin.html` — власник бюджету

1. **Заявки на витрату.** Фільтр статусу (за замовчуванням «Нові»), кнопка «Оновити», таблиця з кнопками «Схвалити» / «Відхилити». Відхилення відкриває панель з обов'язковою причиною.
2. **Рахунки.** Картки з балансом і позначкою «Відкритий / Закритий для заявок». Під ними форма додавання й редагування; у режимі редагування поле балансу недоступне.
3. **Операції.** Форма доходу чи витрати, пошук, фільтри, сортування, журнал. Операції за заявками позначено «за заявкою» й без кнопок зміни.
4. **Категорії.** Списки витрат і доходів із кількістю використань та форма.

### 2.3 Стани й повідомлення (спільні для обох сторінок)

| Стан | Як виглядає |
| --- | --- |
| Завантаження | Сірий блок з індикатором: «Завантаження рахунків…», «Завантаження заявок…» |
| Порожньо | «Зараз немає рахунків, відкритих для заявок», «Заявок від «Марко» не знайдено», «Заявок із таким статусом немає» |
| Успіх | Зелене повідомлення під формою — лише після успішної відповіді сервера |
| Помилка перевірки | Червоне повідомлення під формою, по одному рядку на кожну помилку; запит не надсилається |
| Помилка сервера | Червоний банер угорі «Немає з'єднання з сервером. Перевірте, чи запущений JSON Server» і стан помилки в списках |
| Підтвердження | Діалог браузера перед видаленням, схваленням і скасуванням заявки |

Макет адаптивний: на ширині до 900 px колонки стають одна під одною, на 375 px немає горизонтальної прокрутки основного вмісту. Скриншоти — у [screenshots/](screenshots/).

## 3. Патерн Repository

**Задача.** Обидві сторінки працюють з тими самими даними: заявками, рахунками й операціями. Без окремого шару кожна сторінка мала б власні адреси API та копії перевірок. Тоді, наприклад, перевірку `amount ≤ balance` легко забути в одному з місць. Крім того, деякі операції змінюють кілька колекцій одразу: схвалення заявки змінює `accounts`, `transactions` і `requests`.

**Рішення.** `FinanceRepository` (`js/repository.js`) надає сторінкам предметні методи й приховує HTTP. Відображення HTML у ньому немає.

На етапі 3 реалізовано методи читання: `getAccounts`, `getAccount`, `getCategories`, `getTransactions`, `getRequests`, `getRequest`, `findRequestsByRequester`. Решту методів із таблиці нижче буде реалізовано на етапі 4.

| Учасник | Файл | Роль |
| --- | --- | --- |
| Клієнти репозиторію | `js/client.js`, `js/admin.js` | Викликають предметні методи, не знаючи адрес API |
| Repository | `js/repository.js` → `FinanceRepository` | Предметні операції, перевірка правил, відкат змін |
| Джерело даних | `js/api.js` → `HttpClient`, JSON Server, `db.json` | HTTP-запити та зберігання |

| Метод репозиторію | HTTP-запити | Предметне правило |
| --- | --- | --- |
| `getAccounts()`, `getCategories()`, `getTransactions()` | `GET /accounts` … | — |
| `getRequests({ status })` | `GET /requests?status=new&_sort=createdAt&_order=desc` | — |
| `findRequestsByRequester(name)` | `GET /requests?requesterName_like=^Олена$…` | Ім'я без урахування регістру, точний збіг |
| `createRequest(data)` | `GET /accounts/:id`, `GET /categories/:id`, `POST /requests` | Рахунок відкритий, категорія — витрата, `amount ≤ balance` |
| `updateRequestStatus(id, action, { reason })` | `GET /requests/:id`, `PATCH /requests/:id` | Перехід дозволяє стан заявки (State) |
| ↳ `approveRequest(request)` | `GET /accounts/:id`, `PATCH /accounts/:id`, `POST /transactions`, `PATCH /requests/:id` | `amount ≤ balance`; відкат при збої |
| `createAccount`, `updateAccount`, `deleteAccount` | `POST`, `PATCH`, `GET …?accountId=`, `DELETE /accounts/:id` | Не видаляти рахунок зі зв'язками |
| `createCategory`, `updateCategory`, `deleteCategory` | `POST`, `PATCH`, `DELETE /categories/:id` | Не видаляти використану категорію й не змінювати її тип |
| `conductTransaction`, `editTransaction`, `deleteTransaction` | `GET`, `PATCH /accounts/:id`, `POST` / `PATCH` / `DELETE /transactions` | Баланс ≥ 0; операцію за заявкою не змінювати |

**Чому доречно.** Правила записані в одному місці й однаково діють для обох сторінок. Репозиторій приймає `HttpClient` у конструкторі, тому його можна перевіряти на окремому JSON Server з тестовою копією даних.

## 4. Патерн State (GoF)

**Задача.** Дії із заявкою залежать від її статусу. Нову заявку можна схвалити, відхилити або скасувати, а розглянуту — ні. Якщо писати перевірки через `if (status === …)` у кожній кнопці та в кожному методі, правила переходів розпорошуються. Тоді легко, наприклад, схвалити вже скасовану заявку з іншої вкладки.

**Рішення (реалізація — етап 4, файл `js/request-states.js`).** Кожен статус — окремий об'єкт стану. Заявка (контекст) делегує йому дії.

| Учасник GoF | Клас у `js/request-states.js` | Роль |
| --- | --- | --- |
| Context | `ExpenseRequest` | Зберігає дані заявки й поточний стан; методи `approve()`, `reject(reason)`, `cancel()` делегує стану; `changeState()` перемикає стан і готує зміни для PATCH |
| State | `RequestState` | Спільний інтерфейс; за замовчуванням дія заборонена (`DomainError`) |
| ConcreteState | `NewState` | Дозволяє `approve` → `approved`, `reject` → `rejected` (з причиною), `cancel` → `cancelled` |
| ConcreteState | `ApprovedState`, `RejectedState`, `CancelledState` | Кінцеві стани: жодна дія не дозволена |

Де використовуватиметься:

- **Repository** (`updateRequestStatus`) створює `ExpenseRequest` зі **свіжої** версії заявки, отриманої з сервера, і викликає дію. Якщо перехід заборонений, `DomainError` виникає ще до будь-яких змін. Так адміністратор не схвалить заявку, яку член родини щойно скасував в іншій вкладці.
- **Інтерфейс** показує лише дозволені кнопки: `getState(status).adminActions` на `admin.html` і `clientActions` на `client.html`.

**Чому доречно.** Новий статус — це один новий клас стану, без правок у розгалуженнях по всьому коду. Правила переходів зібрано в одному файлі.

Діаграма станів — [uml/request-states.png](uml/request-states.png).

## 5. Сценарій схвалення заявки (основна операція)

1. Адміністратор натискає «Схвалити» й підтверджує дію в діалозі.
2. `GET /requests/:id` повертає свіжу заявку. `ExpenseRequest.approve()` перевіряє, що вона нова (State).
3. `GET /accounts/:id` повертає свіжий баланс. `checkFunds` перевіряє `amount ≤ balance`; якщо коштів бракує — відмова, нічого не змінено.
4. `PATCH /accounts/:id` записує новий баланс.
5. `POST /transactions` створює операцію-витрату з `requestId`. Якщо цей запит не вдався — баланс повертається.
6. `PATCH /requests/:id` записує `status: "approved"` і `transactionId`. Якщо цей запит не вдався — операція видаляється, а баланс повертається.
7. Сторінка перезавантажує дані й показує повідомлення з новим балансом. Член родини бачить «Схвалена» після «Оновити».
